Agent Skills for Documentation

Developers now ask AI first and open the docs only to check the answer. With the Google Cloud Documentation team, I led research and design on Skills — workflows grounded in official docs that people and AI agents can both follow.

Role
UX designer & researcher in a team of four
CLIENT

TOOL

METHODS

“When developers stopped reading docs and started prompting AI, Google Cloud's documentation had to learn a new language.”

01 — Context

AI is becoming the first reader

Google Cloud's documentation supports more than 100 cloud services, but people increasingly reach it through AI rather than reading it directly. The documentation team put the shift plainly:

“AI has fundamentally reshaped how people seek, explore, and consume information.”

  1. AI agents are reading documentation.48% of doc views by AISource: Write the Docs 2026 Conference
  2. AI-generated code is increasing.50% → 75% in 6 monthsFall 2025 to April 2026 · Source: Google Cloud Next 2026
  3. Technical documentation is becoming infrastructure for AI agents.Source: Write the Docs 2026 Conference
02 — The challenge

The docs are no longer the first stop

Google Cloud documentation is organized by product. It is an authoritative reference — but people reach for it differently now. They move between AI tools, search, community answers and the official docs, and the docs often come last.

The project started as docs.cloud.google.com launched as a dedicated home for technical documentation. Our guiding question: how should the documentation experience evolve when AI is increasingly the first reader?

03 — Discover

Mapping the friction first

  1. 01 · Friction logsAI became my starting point; the docs became where I checked.
    • I asked Gemini how to deploy to Cloud Run first, and opened the docs only to confirm its steps.
    • The “Get started” page read as an overview, not a path, and “Start free” didn’t say what happens next.
    • A build error led me to concept pages, not the error itself — I solved it in Gemini by searching the error ID.
    • The BigQuery ML tutorial was the smoothest: its step-by-step structure made it easy to recover.
  2. 02 · Competitive analysisProduct-centric docs make cross-service work hard.
    • Google Cloud and AWS organize by product, which raises cognitive load for workflows that span services.
    • Microsoft Learn’s guided learning paths reduce decision fatigue instead.
    • I saw an emerging pattern: AI-readable docs — structured metadata, llms.txt — that coding assistants can act on directly. It became the seed of Skills.
  3. 03 · SWOT and literature reviewA strong reference, but not a task guide.
    • Strength: an accurate, searchable reference. Weakness: a fragmented, product-centric structure that favors completeness over getting a task done.
    • The literature agrees that information-seeking is non-linear (Ellis, 1989) and that developers move between docs, search, forums and AI (Zhang et al., 2023).
    • Interactive, code-centered formats reduce cognitive load (Kühn et al., 2023).
  4. 04 · User segmentationEach segment needs the docs for a different job.
    • Builders, my primary segment, start with AI and need accurate docs to verify its output.
    • Entry-level developers grew up on AI summaries rather than manuals — the most critical emerging group.
    • Experienced developers treat the docs as the source of truth, but want them faster to consume.
Across all four

I found a trust gap: people rely on AI for discovery, but need documentation as a precision anchor to verify technical accuracy.

04 — Contextual inquiry

Watching developers solve real tasks

9 participants: builders, engineers and future developers, to complete four realistic Google Cloud tasks: building an app, fixing a permission error, troubleshooting BigQuery and exploring models in Vertex AI.
To study how, when and why they switched between AI, documentation and google search.

Key insight

Developers rarely read documentation sequentially or proactively. They consult it reactively, as a precision anchor when things break — and prioritize interactive, actionable, visually clear steps.

  1. AI is the new front door.78% participants used AI before documentation“AI first, then human experience, and then last thing, documentation. Because documentation is very long.” – P7
  2. Action over concept.100% of participants reached for tools beyond documentation to finish a task“Documentation is fine. It’s just that it should have been guiding me to the console or UI that allows me to add or remove permissions.” — P6
  3. Tasks cut across products.0% of participants completed a task using a single doc page“I got the information that I needed, but I feel like it wasn’t enough to continue as a person who first got introduced to this problem or assignment.” — P5
05 — The pivot

Information seeking → execution

  1. 01The assumption“Redesign documentation in the AI era” — but January’s segmentation was all human: builders, entry-level, experienced. AI was a tool people used. Not yet a reader.
  2. 02The evidenceSame findings, read differently: 7 of 9 reaching for AI first, zero finishing on a single page. Not just how people searched — proof of who’s actually reading.
  3. 03The correctionThe reader changes too. Documentation was written for a human who seeks, then acts. Increasingly, the one executing is the agent, and the human’s role shifts to approving what it does.
06 — Solution

Documentation Skills

Skills transform static documentation into actionable workflows that help users move from problem to resolution faster. Each Skill is a SKILL.md an AI agent can follow, grounded in official Google Cloud documentation. Skills enable AI agents to:

  • Follow structured instructions — accelerate task completion
  • Reduce ambiguity — reduce cognitive load
  • Execute repeatable workflows — improve workflow consistency
  • Deliver consistent outcomes — grounded in official docs
  1. 01OverviewEvery Skill opens with what it does, not how — the problem it solves, its category, and what changes on your system if you run it. Before “Execute” ever appears, a user already knows whether this is the right fix.
  2. 02ExecutionOne Execute action, plus a copyable command for the agent the user already works in — Antigravity, Claude Code, Codex, Cursor or Gemini CLI.
  3. 03InstructionClarifying questions, prerequisites, numbered steps and validation logic, each tied back to the documentation source behind it.
Skill detailAnatomy of a Skill

The Skill page answers the questions a user asks, in the order they ask them. The human-facing layer is built from the same SKILL.md the agent reads, and every step links back to the original documentation.

Proposed success metrics. Metrics follow Google’s HEART framework (Happiness, Engagement, Adoption, Retention, Task success), with safe execution added as a guardrail metric.   3. AdoptionSkill runs per entry point — prompt box, library, introduction page and documentation pages.

09 — Usability testing

Five patterns from testing

  1. 01Skills concept confusionAI familiarity predicted understanding: engineers who used AI daily got it; others struggled.
  2. 02Execute button opacityTwo of three participants were unsure what Execute would actually do.
  3. 03Context over standalone docsEveryone preferred Skills inside the environment where they were already working.
  4. 04Search over browseTwo of three skipped the home page and library and went straight to search.
  5. 05Trust through context fitTrust came from the Google source and a close match to their situation — not from reading the code.
10 — Iteration

A fix for every finding

Each pattern became a recommendation for the next iteration. The highest priorities: a “What is a Skill?” explainer, an Execute button that states its outcome, a preview of the execution mode, trust signals such as source attribution, and a Skills flow embedded in the console.

  • Lead with search; deprioritize browsing the library.
  • Separate what people read from what the AI agent executes.
  • Test alternative command names, and use progressive disclosure for the full documentation.
